## Comment lire le CSV

- `arc` : `000` est la partie XXX (`e9c3c53`), `001` est cet arc. `ordre` est le rang chronologique dans l'arc. `horodatage` est la date d'auteur du commit (UTC).
- `message` : la chaîne (1, 2 ou 3) dont le commit est la réponse. Les commits du 7 octobre avant le masque binaire et ceux du 8 octobre vont dans 1 (le workflow lancé par le message 1) ; les deux commits du masque binaire vont dans 2 ; ceux du 9 octobre vont dans 3. L'arc 000 est compté comme une seule chaîne (1) : ses deux messages sont traités ensemble dans un seul document.
- `script` : le script du dépôt qui écrit la sortie, ou dont la sortie reprend les nombres. Vide pour ce qu'un agent ou l'auteur écrit à la main. Plusieurs scripts : séparés par « ; ». Les scripts ne sont pas des lignes : ils sont dans cette colonne et dans le § c.
- `entree`, `sortie` : chemins depuis `chevre-optique/`. `ext:` désigne un fichier hors du dépôt (la copie locale de dzoba/venn17, `/home/user/dzoba/venn17/`). `msg:N` désigne le message N de l'auteur. Pour une fiche, `entree` donne ses données.
- `type_sortie` : les six valeurs du gabarit. Arc 000 : donnees_externes 3, resultats 1, figure 3, document 2, config 2. Arc 001 : resultats 16, document 35, fiche 56, config 13, donnees_externes 3, figure 7. Les lignes `donnees_externes` sont des entrées : elles ne comptent pas dans les parts du § g.
- `observation` : les numéros de fiches liées, séparés par « ; ». Pour un résultat ou une figure, ce sont les fiches qui s'en nourrissent, même écrites plus tard.
- Une même sortie peut avoir plusieurs lignes : une par commit qui la change de façon notable (la fiche 002 a quatre lignes : création, révision, deux compléments). La dimension d'une ligne est expliquée en annexe.
- Les dossiers lisent aussi les parties de leur liste (`plan-001.md`, § 1.1 à 1.8) : `entree` ne donne que le plan, le script et ses résultats.

L'auteur demande, pendant que le workflow tourne : « 0,37 à 27 ? Quel est ce masque binaire ? … signed/unsigned ? … le seuil de quoi, quel chapitre, quel script, quelle image ? … les canaux RGB, 1/3 + 10/3 ? »

## Annexe : comment j'ai classé les lignes du CSV

Les règles sont fixées avant de compter. Ce sont mes choix ; ils se discutent.
1. **Une fiche** prend sa dimension principale (la première du champ « dimension »).
2. **Une sortie propre à une partie** (résultats, figure, document) prend la dimension de la partie dans `plan-001.md` (§ 1.10, `parties_dimension_naive`) : XI D2, XIV D5, XVIII D3, XIX D2, XXIII D3, XXVII D7, XXVIII D6, XXIX D6, XXX D3. Une figure à six panneaux de dimensions différentes prend celle de la majorité de ses panneaux : ae1 D6, ae2 D4, ae3 D3.
3. **Un dossier** prend la dimension dominante de sa projection dans `plan-001.md` (§ 1.10) : corde D1, moitiés D1, bases D2, grain D3, lumière D4, aiguilles D5, ombres D6, méthode D7.
4. **Le recueil et la révision eux-mêmes** (CLAUDE.md, README, index, plan, synthèse, vérification croisée, sorties JSON, résultats et figures de `revision_001.py`) : D7. Exception : quand le commit n'ajoute qu'un test sur un sujet précis, la ligne prend la dimension de ce sujet. Masque binaire (`3bf627f`, `1fbf39c`) D3 ; trois énoncés des dossiers (`84c1336`) D2 ; le « 93 % » (`e1ea425`) D4 ; l'arbre 43/108 (`3a20ebe`) D5.
5. **Une config qui résume une partie** prend la dimension de la partie : CLAUDE.md et README.md à `e9c3c53` (D3), CLAUDE.md à `e1ea425` (D3).
6. **Les données externes** (le dépôt de Dzoba) : D6, parce que ce sont des diagrammes de Venn. Elles ne comptent pas dans les parts.
